# 실험 리포트 작성 방법

리포트는 질문과 결론을 먼저 보여주고, 실행 조건과 원본 측정 자료를 뒤에 배치합니다.

## 첫 화면

```markdown
# [확인한 운영 문제를 드러내는 제목]

> [문제, 바꾼 것과 주요 결과를 담은 한 문장]

![변경 전후를 비교한 그래프](./assets/result.svg)

| 지표 | 변경 전 | 변경 후 | 차이 |
| --- | ---: | ---: | ---: |
| 주요 지표 1 | | | |
| 주요 지표 2 | | | |

**결정:** [결과를 보고 선택한 방식과 적용할 조건]
```

제목만 보고도 무엇을 확인했는지 알 수 있어야 합니다. 예를 들어 `캐시 성능 테스트`보다 `동시 첫 요청 100개를 한 번의 이미지 변환으로 합칠 수 있는가?`가 낫습니다.

그래프에는 축 이름과 단위를 직접 적습니다. 색만으로 선이나 막대를 구분하지 않고 이름이나 모양을 함께 사용합니다. 목표선을 그었다면 왜 그 값을 목표로 정했는지도 설명합니다.

## 본문에 들어갈 내용

### 확인할 문제

운영 중 어떤 결정을 내려야 해서 이 실험을 했는지 한 문장으로 씁니다.

### 왜 중요한가

이 문제가 사용자 응답 시간, 장애 범위 또는 비용에 어떤 영향을 주는지 설명합니다.

### 예상과 선택 기준

결과를 보기 전에 예상한 내용과 어느 조건에서 어떤 방식을 선택할지 적습니다. 측정이 끝난 뒤 기준을 바꿨다면 그 이유도 남깁니다.

### 실행 환경

- 코드 커밋과 실행 날짜
- 구성도
- AWS 리전, 인스턴스나 실행 환경, CPU·메모리 제한
- 부하 생성기를 실행한 위치와 네트워크 조건
- 사용한 이미지와 사용 조건
- 동시 요청 수, 실행 시간과 반복 횟수
- cold/warm cache를 구분한 방법
- 메트릭을 수집한 방법

### 변경 전후

먼저 변경 전 결과를 보여주고, 다음으로 무엇을 하나 바꿨는지 설명합니다. 여러 내용을 한꺼번에 바꿨다면 각각의 효과를 나눠 설명할 수 없다는 한계를 적습니다.

### 결과

첫 화면의 결론을 뒷받침하는 그래프와 표를 둡니다. 응답 시간뿐 아니라 오류율, 재시도, 중복 작업, CPU, 메모리와 비용도 필요한 만큼 함께 봅니다.

### 결정

- 어떤 방식을 선택했는가
- 그 대신 포기한 것은 무엇인가
- 어느 요청량과 자원 제한에서 유효한가
- 어떤 수치가 되면 결정을 다시 검토할 것인가
- 배포 취소나 기능 중단 방법은 무엇인가

### 장애가 났을 때

장애를 만든 실험은 장애 시작, 탐지, 사용자 영향, 대응 시작과 복구 시각을 한 그래프에 표시합니다.

### 한계

개인 환경의 부하 생성기로 확인할 수 없는 실제 서비스 특성, 짧은 실행 시간, 입력 이미지의 편향과 AWS 환경 차이를 적습니다.

### 다시 실행하는 방법

AWS 자원 생성, 데이터 준비, 부하 실행, 결과 수집, 그래프 생성과 자원 제거 순서의 명령을 제공합니다. 예상 비용과 원본 자료 위치도 함께 적습니다.

## 파일 구성

```text
experiments/<experiment-id>/
  README.md              실행 계획과 데이터 형식
  workload/              부하와 장애를 만드는 코드
  results/<run-id>/      원본 측정 자료와 실행 환경 정보
  analyze/               집계와 그래프 생성 코드
reports/<experiment-id>/
  README.md              결과 리포트
  assets/                생성한 그래프와 구성도
```

그래프를 손으로 고쳐 수치와 모양이 달라지게 하지 않습니다. 원본 측정 자료에서 다시 만들 수 있어야 하며, 리포트의 숫자가 집계 결과와 맞는지도 자동으로 확인합니다.
